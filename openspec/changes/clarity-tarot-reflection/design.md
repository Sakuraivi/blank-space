## Goals / Non-Goals

**Goals:**

- 一次体验围绕一件事，让用户辨认出至少一个具体的区分、取舍、资源或待验证事项；留下可再次阅读的整理。
- 降低表达负担：默认一问一答，随时能改、跳过、停下。完整度由当前问题决定。
- 将“温馨”体现在尊重表达、清晰反馈和舒适阅读；牌面只占一个轻量且有用的环节。
- 使每个成品结论能追溯到用户表达或明确确认；保留尚未知晓的部分。

**Non-Goals:**

- 读取未表达的思想，诊断人格/疾病，预测关系走向，替用户判断他人内心。
- 首版提供 78 张牌、正逆位、每日运势、复杂牌阵、连续打卡或心理评分。
- 把一件开心小事强行解释成矛盾、创伤或改善任务；给每次整理虚构“深刻洞见”。
- 本轮修改生产代码、调用用户真实 Key、调整现有预算或发布版本。

## Decisions

### 1. 产品核心：一页可以带走的清楚

首页主句建议：“把心里的事，慢慢理清。”说明：“从一件小事开始，分清发生了什么、自己在意什么，以及还有哪些选择。”保留三个直接进入写作的场景入口：留住一个片刻 / 理清一件事 / 想想一个选择；通用 CTA 只打开不预选主题的写作页，不再与三张主题卡形成选择后再继续的双重门槛。

成品总称“这次的整理”。“理清了什么”是内容质量目标，不能作为每次必然达成的 UI 承诺。若尚未理清，显示“目前的线索”。

### 2. 一条主线，三种适度深度

| 场景 | 最值得回答的问题 | 通常结束条件 | 成品重点 |
| --- | --- | --- | --- |
| 留住片刻 | 哪个细节值得留下，它为什么对我有意义 | 细节 + 用户认可的意义已经足够，允许仅留原话 | 片刻、值得留住的感觉/条件、想留下的一句话 |
| 理清困扰 | 哪些是经历、哪些是解释；真正卡在哪里 | 形成一个用户认可的区分，或识别必须向现实确认的信息 | 事情、想法与感受、在意、这次看清的、未知、可选一步 |
| 权衡选择 | 两边分别保留与牺牲什么；决定还缺什么 | 有个人标准及一个关键取舍/信息缺口；不要求当场决定 | 选项对照、个人标准、实际限制、仍待了解、可逆尝试 |

三种路径共享状态与修正机制，最终页面按内容组织。困扰是首个实现和质量验证的纵向切片；片刻与选择沿同一契约接入，不复用困扰的全部标题。

### 3. 主流程与每屏职责

```text
Express --> Focus + first useful question --> Explore --> Review --> Keep
                         ^                     |
                         +------ edit ---------+
                                              |
                          optional lens <-----+
```

**表达页。** 一个输入区，场景只改变开头提示。按钮“开始梳理”。紧邻按钮写“点击后，会把这次表达交给 AI 帮你梳理。”源服务信息放设置中，正文不展示厂商/模型。已明确是本地记录时按钮与说明相应变化。

**对齐关注点。** 用户已明确“我想知道为什么难受”时不再另问目标；在对话顶部显示“这次想理清：……”并可改。若混有多件事，只问“这一次，你最想先理清哪一件？”按钮候选是省力输入，不代替用户作心理判断。

**一起理清。** 主体每轮只含三件东西：简短且针对实际内容的回应、最多一条新出现的重要区分、一个有用途的问题。不要每轮先重复“我听见了/谢谢你分享”，不要同时问原因、感受、需要和行动。

- 当前内容下方始终可“先整理到这里”；此前回答可回看并编辑。
- 宽屏右侧“这次的线索”只显示最多三条摘要；展开后查看完整分类。手机把摘要收成当前问题下方的“已经记下的线索”，不挤占输入区域，不做悬浮遮挡。
- 重要的新解释用“这样理解贴近吗？”提供“贴近 / 改一下 / 暂时不确定”。这些是本地确认，不发送请求。用户可以直接编辑，不需要逐句做审核员。
- 最终确认前全部内容仍为草稿。事实分类的准确性由应用约束、模型质量检查和修正共同承担；“用户确认”只表明记录符合表达，不代表客观事实已经核验。

**收尾预览。** 显示一页完整草稿，每节可编辑、暂时移除和恢复。仅对仍未确认的推断标记“待确认”；原话与忠实归纳不要求逐项点选。按钮“留下这份整理”完成一次总确认。若有未决推断，提供“先不放入”或“我认可这句”，不阻止保留其他内容。

**留下。** 展示本机保存、导出图片、下载文字；保存行为真实发生后才显示成功。原始对话不会自动随成品导出。返回修改继续同一份草稿，不重新生成。首页样例标“虚构示例”，采用同一成品渲染器，避免样例与实际产出脱节。

### 4. 提问机制：先找缺口，再选表达

每个问题需要内部 `target`：补齐事件 / 区分解释 / 找到在意 / 比较取舍 / 确认未知 / 选择小步。它还需要当前用户材料依据和预期补充的槽位。缺口已经回答则不再次问同义问题；用户纠正优先于向下一阶段推进。

优先次序：理解错误 → 关键事实不足 → 混合了观察与推断 → 目标相关的需要或取舍 → 现实中才能确认的信息 → 用户主动希望的下一步。不是六道必答题。

本轮只增加 1–3 条有用候选线索；不要求每个字段填满。内容足够时建议收尾；信息无法从自省获得时保留未知；用户疲惫或不想回答时立即允许结束。三次没有进展也不能换措辞继续追问。

### 5. 塔罗：一次可选的视角切换

把原本固定流程中的“抽卡步骤”移除。在关注点明确后，提供低调的“借一张牌，换个角度”。无需先抽牌才能对话。默认推荐与当前问题匹配的一张，用户也能看到其他两个视角的明文含义。文案只需首次说明：“借牌面想一想，答案仍从你的经历里找。”

| 视角入口 | 牌面灵感（次级显示） | 可用问题方向 | 禁止推导 |
| --- | --- | --- | --- |
| 看清事情 | 天平 / 正义 | 哪些亲历，哪些推测；有什么反例或缺失信息 | 谁对谁错、因果报应、对方必然如何 |
| 听见在意 | 灯 / 隐者 | 这件事中希望被满足、保留或尊重什么 | 你注定孤独、隐藏人格、未经表达的创伤 |
| 找到选择 | 手 / 力量 | 能影响的部分、可逆尝试、能接受的代价 | 忍耐就是力量、必须原谅、未来必然成功 |

牌正面是简洁原创图案、一个视角标题和一个相关问题，最长一两行。不要把一大段牌义插入对话，也不做七彩卡片墙。只在翻开时有 180–240ms 的轻量过渡，减少动态偏好下立即显示。

**无额外调用的具体实现：** 本轮正常回应已经带有一个有依据的 `nextQuestion` 和匹配的 `lensId`。翻开推荐牌只是以牌面呈现同一个问题。另两个视角使用本地问题库的开放式问句；例如“这件事里，哪些是你亲眼看到或亲耳听到的？”用户选择后，只有发送回答才调用模型。系统不伪称随机命中命运，也不把同一个问题包装成两轮对话。

卡片和问题不是事实来源；用户回答才是新材料。选择某张牌本身不推出任何人格、情绪或结论。报告默认不印牌名；需要回看时折叠显示“帮助我思考的角度”。

### 6. 成品设计：阅读页与工作草稿各司其职

困扰路径最多六节：

1. **事情的轮廓**：用户陈述的可观察经过，短而准确。
2. **当时的想法与感受**：解释与感受分别写明，不混进事实。
3. **我在意的**：用户认可的期待、边界或价值。
4. **这次看清的**：与初始问题相关的具体区分、关系或修正；没有就改名“目前的线索”。
5. **还不知道的**：现实中需要确认的部分，允许留白。
6. **我愿意尝试的一步**：仅在明确选择后出现；说清做什么及观察什么，允许不行动。

“我在意的”和“这次看清的”若表达完全相同就合并，不能换词重复凑六节。空节不展示。正文目标 250–450 汉字只是版式参考，不是强制字数；材料少就短。

选择路径使用紧凑对照：每个选项的吸引点、代价、未知均来自用户表达；无数字权重时不用算法分数。片刻路径只需 2–3 节，不出现问题、修复和任务标题。

**视觉方向：安静的阅读页 + 一张有记忆点的视角牌。** 沿用留白现有温暖底色，收紧凌乱的标题、阴影和段落层级。外层不再堆同等大小的圆角块。报告左对齐；正文宽度约 36–40 个汉字；标题统一一套宋体，正文统一系统黑体。核心页面不依赖远程字体。

| Token | 选择 |
| --- | --- |
| 背景 / 纸面 | `#F5EEE7` / `#FFFCF7` |
| 正文 / 次级文字 | `#34342F` / `#69665E` |
| 交互强调 / 温和衬色 | `#70445F` / `#E8EBD8` |
| 标题字体 | `Noto Serif SC`, `Source Han Serif SC`, `Songti SC`, serif，本地可用优先 |
| 正文字体 | `PingFang SC`, `Microsoft YaHei`, sans-serif |
| 尺度 | 正文 16–17px，行高 1.8–1.9；节标题 15–16px 中等字重；页标题 26–32px |
| 间距 | 段内 12–16px，节间 28–36px；移动端左右 20–24px |

已作的自我修正：暖底 + 大宋体 + 卡片墙容易再次变成模板。保留用户选择的温暖方向，把差异放在“正文旁逐渐浮现的真实线索”和唯一的视角牌上；其余靠对齐、留白和具体内容建立温度，不加星空渐变、漂浮装饰或大段文艺口号。

### 7. 状态、模型和证据的责任边界

应用拥有 `express / exploring / reviewing / kept` 状态、请求版本、确认/排除/恢复和保存结果。模型只能提交候选内容和建议的下一问题，不能直接进入下一状态或标记完成。

会话包括用户原话事件、当前目标、类型化的候选线索、用户修订和确认事件、问题历史、当前牌面视角、草稿版本。线索种类至少区分 event / thought / feeling / need / option / tradeoff / unknown / insight / action。每条拥有来源 ID、派生类型和稳定 ID。可见摘要最多三条不等于存储只保留三条。

模型提出对现有条目的替代时以 `supersedes` 表达，不能直接覆盖已确认或用户改写内容。用户回改上游材料后，相关候选变为“需要再看一下”；历史内容和当前手动编辑仍可恢复。不能因为 `evidenceIds` 存在就视为语义有依据；实现前需用完整示例检查事实增补、暗含判断和上下文遗漏。

采用增量候选响应而非每轮输出整份长报告：简短回应、最多三条线索提议、一个问题或收尾建议、可选行动。应用把候选合并到工作草稿；收尾时按场景模板排列已有内容，不再付费调用一次“总结模型”。新认识必须在对话中已经出现、经过修正/确认，不能在最终页突然冒出。

**保存契约的具体选择：** 工作草稿与最终记录分离。新增本地记录 `formatVersion: 2`，保留现有标识/日期/场景，成品 `review.blocks` 最多六块，限定为 `text` 或 `option-comparison`。后者保存选项名、吸引点、代价、未知的纯文本行，禁止模型 HTML；阅读、图片与文字导出共用同一投影。旧版无版本字段的 `review.sections` 通过只读适配进入 text 块，直到用户明确保存修改才写成 v2；不批量重写用户历史。旧记录解析、清空敏感材料和导出逻辑需要同步更新，且单独验证兼容。不会把表格 Markdown 塞进旧 text 字段后假设原渲染器自然支持。

提示词分三层：平台长期边界 → 当前场景/阶段/本轮缺口与允许行为 → 明确标记为数据的用户材料。各厂商复用同一语义策略，适配器处理请求格式差异。结构校验、来源校验、版本校验和保存过滤由代码保证；语义忠实与提问价值通过样本评估，不声称系统提示词能保证一切。

### 8. 调用与失败设计

继续使用 `/api/ai/generate`，新增独立 `flow: clarity-v2`，旧协议保持原行为；非法 flow 拒绝。复用 source/config/consent/defaultRevision 绑定、reservation、requestId 去重、并发和晚响应防护。

五次现有调用上限下，计划是首次理解一次、最多三次补充回答、一次由用户明确请求的可选行动；这只是资源安排，不强迫走满。前四次若已经用于对话，第五次不能同时被隐式重试和行动占用。剩余额度以服务端结果为准。翻牌/换牌、回看、确认、编辑、收尾排版均为零调用。

供应商有较小输出上限，故禁止一次返回整份九类报告。新契约应覆盖最小路由输出容量的定向测试；请求超过字节边界时明确请用户缩短，绝不静默丢掉修正或上游证据，也不先预留计费额度。对于已达到会话上限的情形，仍可编辑并保存当前材料，提示“先把已经清楚的留下”，不得宣称问题已解决。

请求进行中输入保留，可取消。用户编辑/退出/换服务后旧响应不能写回。失败不自动重试、不清空输入、不以 canned 文案冒充 AI 输出；提供“重新发送”和“按已有内容整理”。发生明显现实危险的输入时退出牌面玩法，给出与所在环境相符的支持导向，不作疾病诊断；相关内容策略需要专项核验。

## Risks / Trade-offs

- [仍可能只有精致复述] → 以完整输入到成品的语义对照验收；困扰和选择须有具体认知增量。不能靠 UI 截图或 JSON 合法率宣称有效。
- [确认过多破坏轻松感] → 只在关键解释和最终保存处确认；源材料引用可展开，不强迫逐项审计。
- [塔罗吸引注意却干扰问题] → 只用一个可选环节；推荐问题先由实际缺口决定；保留同质量的无牌面路径。
- [牌面提问暗示不必要的问题] → 使用开放式问题库；不贴合时跳过，不把换牌理解成否认用户。
- [用户纠正后模型重新带回错误] → 显式修订事件、候选替代和 stale 状态；针对纠正链路增加行为测试。
- [五次调用不够复杂事件] → 聚焦一个目标、允许保留未知和早停；此版不以增加无限轮数掩盖提问质量不足。
- [手工样例优于实际模型] → 样例标识为目标样本；上线前单独记录真实模型运行证据及失败，不将固定回复预览当效果评估。

## Migration Plan

1. 本轮产出设计与示例，严格校验 OpenSpec；保持线上不变。
2. 先实现困扰路径完整纵向切片，包括来源、纠正、早停和可恢复成品。旧版与新版按 flow 分离。
3. 通过新功能定向验证及内容评估，再接入片刻、选择和牌面。复用后台与模型路由，不迁移数据库或修改管理口令。
4. 新旧记录保持可读；导出由同一场景模板渲染。部署前检查导出图/文字、390px 页面、键盘流程、调用计数及未确认内容过滤。
5. 发布时只切新体验入口；回退入口不删除已保存记录，不回滚忽略新版管理员凭证的旧 Worker。
