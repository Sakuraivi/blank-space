## Context

现有 `public/` 手写前端通过 Vinext 同源 API 调用固定 DeepSeek 适配器。D1 `pilot_requests` 已提供跨请求的总计、会话、并发和幂等门禁；版本 2 的公开流程仍要求体验码，`public/admin.*` 要求 Sites 身份，默认 Key 由旧配置 API 加密存 D1。详见 proposal.md 的变更动机。

用户本轮明确选择：访客可填自己的 Key，不填时用组织者提供的默认 Key。无需为此开放全站配置写权限。用户已自行在生产公开入口填写个人 Key。首次以明确虚构的周末散步片刻进行真实凭据路径冒烟，业务结果为 fallback；已发现 Workers 运行时对重定向参数的兼容缺陷，尚未取得真实供应商成功、内容质量或实际账单证据。设计记录不包含凭据值。

## Goals / Non-Goals

**Goals:** 公开个人设置与明确的凭据来源；固定服务端规则不受客户端替换；复用现有持久账本；原创、温暖且易表达的界面；保留默认本地体验。

**Non-Goals:** 匿名修改全站默认 Key、开放任意 API 地址、多供应商路由、账号/邮箱登录系统、迁移托管、重置本批额度或把预留数当作真实账单。

## Decisions

1. **个人 Key 优先，显式失败。** 生成入口接受可选的个人凭据字段，非空且合法时只用该 Key；留空时使用 `LIUBAI_DEFAULT_DEEPSEEK_KEY` 服务端秘密项。可兼容旧已启用的加密配置作为后备默认来源，但旧全局读写接口继续授权隔离。拒绝“个人 Key 失败后静默切共享 Key”，避免费用来源与用户选择不一致。
2. **个人设置留在当前页面。** 首页提供设置弹窗或同页视图；旧 `/admin.html` 引导到公开设置。页面间导航不通过 URL、存储或 Cookie搬运个人 Key；输入、清除和关闭设置不调用模型。个人 Key 随生成请求经同源 HTTPS到后台，在适配器认证头中使用，不放入上下文或账本摘要。
3. **状态 API描述能力与默认可用性。** 状态不再把“没有默认 Key”简单等同于“AI 关闭”，分别表达个人凭据支持、默认凭据是否可用、批次资格和价格到期。开始实际流程前明确显示当前来源，用户仍须同意把本次材料发送给 DeepSeek。默认 Key 没有配置时不宣称已可免费体验。
4. **统一小额批次。** 个人与默认来源复用现有一份 D1 账本，共同最多 18 次、每会话 5 次、并发 2 次，每次保守预留 ¥0.05。无需新增库表或仅凭个人 Key 绕过当前试用门槛。价格有效期、正文大小、固定端点、取消和候选校验继续生效；异常用量关闭路径不得被环境默认 Key绕开。
5. **每次后台注入场景规则。** 继续使用 `buildContext` 与 `buildModelRequest`，平台规则、模式和阶段写入适配器的指令通道，用户材料单独序列化。模型不能确认、保存或推进业务状态。来源编号只能校验存在性，语义是否忠实仍需真实场景评测。
6. **生活来信的视觉方向。** 本轮采用“傍晚窗边的一封生活来信”，以杏色、莓紫与灯光黄建立层次，原创 SVG生活小景承担主视觉，记录页延续同一语言。参考网易云年度报告的个人叙事与节奏、Finch 的小步表达和陪伴、Headspace 的亲和插画；不复制竞品图像、品牌、角色或完整页面。保留“卡片只提供角度”的产品边界，避免占卜或临床界面暗示。
7. **沿用托管和访问受众。** 本轮不迁出 Sites、不更改域名/受众。构建完成后按现有项目 ID 发布，服务端秘密通过托管控制面配置；默认秘密缺失不是发布阻塞，页面须如实提示并保留个人 Key和本地路径。

8. **使用 Workers 支持的重定向策略。** 供应商请求使用 `redirect: 'manual'`，显式拒绝 3xx，并继续拒绝非固定端点、已重定向或响应 URL不匹配的结果，不跟随 Location。不能使用 `redirect: 'error'`：Cloudflare Workers在构造 Request时即抛出 TypeError，不会发送请求。采用 manual兼容运行时，同时保留防止认证头被带往其他目标的边界。[Cloudflare Request 文档](https://developers.cloudflare.com/workers/runtime-apis/request/)
9. **诊断记录采用显式白名单。** 应用诊断模块仅记录 `event`、`requestId`（UUID）、`stage`、`status`、`reason`；不含耗时或usage，后两者分别从Worker trace及持久账本核验。不记录 Request对象、原始异常、认证头、Key、用户材料、完整响应或提示词。API HTTP 200与业务成功分开，fallback不能当作上游完成。记录时机位于最终safety/config守卫之后，记录实际返回的受控结果，避免已被撤销的候选仍记为成功；日志白名单测试须验证无凭据/无原文。

## Risks / Trade-offs

- [公开默认额度可被耗尽] → 用户已选择无体验码；保留持久总计、会话、并发门禁，当前批次仍有硬调用上限。会话 ID不是实名身份，不宣称每人限额。
- [个人 Key 泄漏] → 仅内存、固定服务端传输目标、保存导出白名单、受控错误、无 Key日志或提示词；刷新后不恢复。服务商和托管层的常规请求处理仍需在数据说明中告知。
- [个人 Key 也消耗本批名额] → 清楚说明这是本轮试用范围；未来如要独立个人额度，应另行定义账本归属和费用约束，不在本次顺手扩展。
- [默认凭据变更或异常停用被绕开] → 请求配置版本与默认来源一致，运行时停用状态在所有凭据选择前检查；环境 Key不自动解除停用。
- [暖感被主观偏好误判为完成] → 桌面与 390 像素截图审查，检查颜色层次、阅读、场景连续性和控件；真实亲友反馈另行记录。
- [离线样例被当作模型效果] → mock标注、独立登记真实连接/质量/账单待验，不把部署成功或自动化数量当作语义正确证明。
- [Node mock通过但 Workers参数不兼容] → 对受限运行时使用支持的 Request参数，并增加构造或运行时兼容验证；首次生产失败作为独立回归案例，不能仅靠 fake fetch证明真链路成功。
- [排错时泄漏凭据或原话] → 诊断字段显式白名单、受控错误码；不采集原始异常/请求/响应，不使用 Key指纹替代身份；日志验证与内容质量验证分开。

## Migration Plan

1. 保留版本 2 和旧账本，落地公开个人设置与状态/生成契约，测试个人优先、留空默认、无默认、无效个人 Key、无登录和不泄漏凭据。
2. 整合原创 SVG、首页和全流程样式，完成本地记录、mock AI、设置清除/刷新及移动尺寸浏览器验收。
3. 执行相关自动回归、结构校验和最终构建，再将精确源码与产物发布到既有公开站点。生产核验个人设置可进入、无 ChatGPT 门槛、默认状态和旧全局接口仍隔离。
4. 用户自行在托管秘密项填写默认 Key，或在公开设置填写个人 Key后，以虚构材料做少量真实模型试跑，所有调用计入同一批 18 次。真实凭据不得发到聊天里。
5. 如需回滚，恢复先前版本的应用产物；保留已有 D1 账本和秘密，回滚不退额度、不重置测试批次。

- 日志在最终safety/config守卫后输出实际受控原因，不记录原文、凭据或原始异常。

这些结果验证运行时参数与边界，不等于真实推理或内容质量。修复后的精确打包构建退出码0，版本4已部署succeeded。第二次真实凭据路径取得供应商受控错误 `provider_balance_low`，模型成功、内容、纠正、usage和实际账单仍待用户账户具备可用余额后验证；版本3的93项/失败请求保留为历史。
